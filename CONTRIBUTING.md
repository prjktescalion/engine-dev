# Contributing

## Thank you

First of all, that you so much for considering contributing to Project Escalion. We greately appreciate the time and effort you put into the project

## Introduction

Following these guidelines helps to communicate that you respect the time of the developers managing and developing Project Escalion. In return, the developers and managers should also reciprocate that respect in addressing your issue, assessing changes, and helping you finalize your pull requests. We strive to create a respectful environment, where people feel safe contributing regardless of their backgrounds, ethnicity, origin, religious beliefs, sexual orientation, and so on. 

We welcome all contributions, including but not limited to:

* Improving Documentation
* Bug triaging
* Writing Tutorials
* Opening issues in the issue tracker
* Conducting productive discussions
* Code contributions
  * Code contributions should be well documented.
  * LLM Contributions are welcome, but PRs can only be created by humans. The human creating the PR should be incredibly well versed in the changes suggested, and take full ownership/responsibility.
  * We may schedule a short call/meeting to discuss a PR, to ensure quality.

## Code Contributions

For any Code Contribution, we ask that some baseline responsibilities are taken into account:

* Ensure cross platform compatibility for every change that is expected. Currently, the project targets macOS, Ubuntu, Fedora, Debian, and Windows.
* Please enter relevant documentation and code comments. The PR message should include a full report of what changes were made, and why.
* Create issues for any major changes and enhancements that you wish to make. Discuss things transparently and get community feedback.
* Don't add any classes to the codebase unless absolutely needed. Err on the side of using functions.
* Please try to stick to the packages already used in the project. For example, our frontend uses GPUI. Please do not use Tauri or any other frontend package: it muddles up the repository.
* Keep changes and versions as small as possible. Make git commits at every relevant checkpoint. It is much easier for the team to go over your changes if we see the entire roadmap, as opposed to resolving one commit that adds thousands of lines.
* Welcome newcomers and encourage diverse viewpoints. No gatekeeping.

## Issue Reporting

Please use the GH Discussions panel for support questions and general discussions, and reserve the Issue Tracker for actual issues. 

When recording an issue, please provide:

1. Version Number of Project Escalion
2. Your OS Version
3. Last commit hash
4. A detailed description of the issue, with steps to reproduce and screenshots.

As mentioned above, LLM assisted contributions are welcome: as lpng as full ownership is maintained by the person opening the issue.

Feel free to open a discussion if you have any doubts. This document is not final, and will keep changing and increasing as the project moves forward. Once the project gets to alpha (or gets enough contributors), we plan to expand this document with steps or new contributors, bug tagging, extra guidelines, etc.

**Bottom line- Please be respectful, well intentioned, and genuine. Overall, have fun while you're at it.**
